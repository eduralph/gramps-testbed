  the live defect on gramps61. The actual `KeyError` is in the **path-to-home
  filter logic**: `find_path_to_home` (graphview.py:2772) builds a
  `RelationshipPathBetween` filter whose `init_list` does `firstMap[person_handle]`
  and throws when the home person is not reachable in the computed relationship
  map (i.e. active person and home person are in disconnected sub-graphs, or the
  home person handle isn't in `firstMap`).
- **Hypothesis to confirm by reproducing:** the KeyError fires when there is no
  relationship path between the active person and the home person (disconnected
  trees / unrelated individuals), because `init_list` indexes `firstMap` without
  a membership guard. The config-key angle is likely a SEPARATE, already-resolved
  symptom specific to the reporter's stale ini.
- **Fix sketch (pending repro):** in the filter's `init_list` (upstream
  `gramps/gen/filters/rules/person/_relationshippathbetween.py`) OR in
  GraphView's `find_path_to_home` caller, guard the `firstMap[person_handle]`
  lookup — skip handles not present, or short-circuit when no path exists, so
  "no path to home" degrades gracefully (empty/partial graph) instead of raising.
  **Decision point for Claude Code:** determine whether the correct fix is in the
  GraphView addon (caller-side guard) or in gramps core (the filter rule itself).

  bug → `../gramps`, different PR target. If GraphView is calling the filter with
  bad inputs, it's the addon. **This split changes which repo the PR goes to —
  resolve it before writing the fix.**
