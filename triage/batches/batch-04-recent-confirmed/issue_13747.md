## Description
i do regular backups of my family tree (like any good citizen), and would like to keep incremental backups at a minimum.

unfortunately, saving an unmodified DB often changes the on-disk representation (the sqlite3 file).

this even happens when running a simple export like
```
gramps --format gramps-xml -O /path/to/gramps/db/ -e /tmp/test.gramps
```

## Steps to Reproduce
1. create a new family tree
2. import the attached minimal tree (just two persons with custom name types)
3. quit gramps
4. create a backup of the sqlite.db file
5. export the gramps db from the cmdline, with something like
   ```sh
   gramps --format gramps-xml -O /path/to/gramps/db/ -e /tmp/test.gramps
   ```
6. compare the sqlite.db with the backup
7. (if they are the same, go back to step 5 and repeat a few times; it took me three
   attempts to trigger the issue)

## Additional Information
the backup files (.gramps) do not change.

however, i tracked down the issue by running an SQL dump
```
sqlite3 sqlite.db ".dump" > /tmp/x.sql
```

comparing two dumps i see:
```diff
43c43
< INSERT INTO metadata VALUES('name_types','{"type":"set","value":["Test","Test2"]}',X'80048f942e');
---
> INSERT INTO metadata VALUES('name_types','{"type":"set","value":["Test2","Test"]}',X'80048f942e');
```

<b>so the serialization of custom fields values is non-reproducible (as in: creates
different results based on unknown circumstances).

afaict, this *only* happens with custom field values
(in my real tree i have a few fields with custom values, and all of them get
re-ordered randomly; and only these fields are changing)</b>

**Note 3** (prculley - 2025-05-09 22:39)

metadata such as name-types utilize Python 'sets' for their internal representation.
In Python, sets are unordered collections of unique elements. This means that sets do not maintain the order in which elements are inserted. When iterating through a set, the order of elements may appear random and can vary between different runs of the program or even different Python implementations.

For better or worse, Gramps always saves metadata when a db is closed, thus modifying the db. We don't try to track if any of the metadata has been changed, which would be necessary if we were to try to avoid saving unchanged metadata. Some can be changed via plugins/addons, without actually changing user data.

I would not expect this bug to receive a very high priority...
